## 3. Step 詳細

### Step 1: マスタ更新

#### 1-1. 共通マスタ（checklist_options）

| カテゴリ | 追加する選択肢 | requires_text | 方法 |
|---|---|---|---|
| 回復行動 | **カフェ・喫茶** | — | seeder |
| 回復行動 | **（要判断 D：「その他」で繰り返されている回復行動）** | — | **要判断 D** |
| 体の反応 | **体の痛み・不調** | ✓（部位を書く） | seeder |

あわせて **seeder を本番の実態に合わせる**。本番には管理画面から追加された選択肢が4つある（クセ3つ・体の反応1つ）が、seeder には含まれていない。
`ChecklistOptionSeeder` は `sort_order` を配列の位置で上書きするため、**今のまま seeder を流すと本番の並び順が崩れる**。

| 対象 | 対応 |
|---|---|
| `database/seeders/ChecklistOptionSeeder.php` | 本番で管理画面から追加された4項目を、本番と同じ順番で配列に入れる。新しく追加する選択肢は「何もできてない」「その他」の**前**に置く |
| `tests/Feature/...SeederTest`（新規） | seeder を2回流しても件数・並び順が変わらない（冪等）。既存の選択レコードの `checklist_option_id` が変わらない |

#### 1-2. 既存の「その他」を新しい選択肢に付け替える

過去の「その他」の記述のうち、新しい選択肢に当たるもの（カフェ・喫茶が3件、要判断 D の選択肢が4件）を付け替える。
**付け替えないと、新しい選択肢は「追加した日から」しか集計されず、効いた感の比較に過去分が使えない。**

| 対象 | 内容 |
|---|---|
| `app/Console/Commands/ReclassifySelections.php`（新規） | `app:reclassify-selections --from=<option_id> --to=<option_id> --match=<部分一致文字列> [--user=<email>] [--dry-run]` |
| 挙動 | `log_checklist_selections.checklist_option_id` だけを書き換える。**`detail_text`・効いた感・時間は残す**。`--dry-run` では対象行を表示するだけで書き込まない |
| テスト | 一致した行だけ変わる／他のユーザの行は変わらない／効いた感と時間が残る／`--dry-run` では何も変わらない／付け替え先にすでに同じログの選択がある場合（unique 制約）はスキップして報告する |

> 部分一致の文字列はコマンドの引数で渡し、リポジトリには書かない（私的な内容のため）。

#### 1-3. 個人マスタ（check_items：ストレス源）

| ユーザ | 追加 | 方法 |
|---|---|---|
| 対象ユーザ（id=3） | **お金** | **ご本人が「項目を編集」画面から追加**（ユーザ毎マスタなのでコード変更なし） |

- 既定テンプレート（`DefaultCheckItems`）には**入れない**（個人の事情で、新規ユーザ全員に配るものではないため）。
- **過去分への遡りはしない**。過去の「その他」「コミュニティ」への○を、後から「お金」に読み替えると本人の当時の回答を書き換えることになる。お金の記述は自由記述に残っているので、必要なら分析時に参照する。

#### 1-4. 本番作業の手順

```bash
# PR マージ → 自動デプロイ後（seeder は自動実行されない）
ssh cdesvr 'cd ~/Cde/mentallog/mentalLog && docker compose -f docker-compose.prod.yml exec -T php \
  php artisan db:seed --class=ChecklistOptionSeeder --force'
# 要判断 D が「管理画面で追加」の場合はここで管理画面から追加
# 付け替え：まず dry-run で対象を確認 → 本実行
... php artisan app:reclassify-selections --from=19 --to=<新id> --match=<文字列> --user=<email> --dry-run
```

事前事後に `log_checklist_selections` の件数が変わらないこと（付け替えなので件数は不変）を確認する。

### Step 2: フォームの配置変更＋分析3点（スキーマ変更なし）

#### 2-1. コントロール可能度を「くわしく」の外へ

| 対象 | 内容 |
|---|---|
| `resources/views/logs/partials/form.blade.php` | `controllability` を `$extraScores` から外し、「数値（0〜10）」セクションの**最後に任意スライダー**（`optional => true`）として置く。必須にはしない（触らなければ NULL のまま）。持ち越し感は「くわしく」に残す |
| テスト | フォームの「くわしく」より前に `controllability` が描画される／触らずに保存すると NULL |

> 持ち越し感も外に出すかは要判断 E（下記）。

#### 2-2. 期間比較（区切り日の前と後）

| 対象 | 内容 |
|---|---|
| `AnalyticsService::periodComparison(User, from, to, pivot)` | 区切り日の前と後のそれぞれについて：件数・記録率・各指標の平均、ストレス源ごとの○率、クセごとの選択率、「何もできてない」の割合 |
| `AnalyticsController` / `analytics/index.blade.php` | 分析画面に「比較の区切り日」（GET パラメータ `pivot`）を追加。指定したときだけカードを表示する |
| テスト | pivot の当日は「後」に入る／片方が0件でも落ちない／期間外のログは含まない／他ユーザのログは含まない |

#### 2-3. 選択肢の頻度の分母を「選べた日数」にする

| 対象 | 内容 |
|---|---|
| `AnalyticsService::checklistFrequency()` | 戻り値に `available_days`（期間内のログのうち、`logged_on` が選択肢の追加日 `created_at::date` 以降の日数）と `rate` を追加 |
| `analytics/index.blade.php` | 頻度表に「n / 選べた日数」を表示 |
| テスト | 期間の途中で追加した選択肢の分母が、追加日以降の日数になる |

> ストレス源（`check_items`）は×の回答も行として残るため、行数がそのまま分母になる。こちらは `checkItemFrequency()` に `answered_days` を足すだけでよい。

#### 2-4. 「重なり数」カードの注記を直す

`analytics/index.blade.php` の説明と `AnalyticsService::stressSourceOverlap()` の docblock にある「1件→2件で崖（閾値構造）」を、「**重なるほど単調に下がる**（48件で再確認）」に書き換える。ロジックは変えない。

### Step 3: ストレス源の強度（旧フェーズ3・ストレス源のみ）

前回の計画 §5 フェーズ3 をそのまま使う。変更点だけ書く。

| 変更 | 理由 |
|---|---|
| **相手タグの重み（`log_people.weight`）はやらない** | 相手タグの入力が後期は 5件/20日 まで減っている |
| **強度は ○ のとき必須にする**（前回の計画では任意） | 効いた感を「選んだときだけ必須」にした結果、入力率が 0% → 100% になった。同じ形にする。**要判断 F** |

| 対象 | 内容 |
|---|---|
| マイグレーション | `log_check_item_values.severity` smallint nullable ＋ CHECK `1..3` |
| `app/Support/SeverityLevels.php` | `1=軽い / 2=中くらい / 3=重い` |
| `StoreLogRequest` | `check_items.*.severity` を `Rule::in(1,2,3)`。○で未送信なら 422（要判断 F で「必須」の場合） |
| `LogService::syncCheckItemValues()` | ✕なら `severity` も NULL |
| `form.blade.php` | ○を選ぶと補足テキスト欄の横に3ボタン（既存の `[data-toggle-detail]` に追加） |
| `logs/show.blade.php` | 強度ラベルを表示 |
| `AnalyticsService::stressSourceLoad()` | 「同日の強度合計」ごとの日数と平均スコア（`groupByDailyCount()` を再利用） |
| `checkItemFrequency()` | 項目ごとの平均強度を追加 |
| テスト | 前回 T3-1・T3-2・T3-4・T3-5 ＋「○で強度なしは 422」「✕なら強度不要」「過去ログ（強度 NULL）の編集画面が開ける」 |

> 既存ログを編集すると、○の項目に強度を求められる。**過去ログの編集時は必須にしない**（`logged_on` がリリース日より前なら任意）か、そのまま求めるかは要判断 F に含める。

### Step 4: 体力 → 疲労度（旧フェーズ5・B-1）

前回の計画 §5 フェーズ5 をそのまま使う。

| 対象 | 内容 |
|---|---|
| マイグレーション | `logs.fatigue` smallint nullable ＋ CHECK `0..10`。`logs.stamina` の NOT NULL を外す（down では戻さない） |
| `StoreLogRequest` | `stamina` を `nullable`、`fatigue` を `required` |
| `form.blade.php` | `stamina` を外し、`fatigue`（疲労度・高いと疲れている）を必須スライダーにする |
| `logs/show` / `logs/index` / `LogFilterRequest` / `LogController` | `fatigue` を追加。`stamina` は値があるときだけ表示 |
| `AnalyticsService` | `METRIC_LABELS`・`CORRELATION_PAIRS`・`AUTOCORRELATION_PAIRS` に `fatigue` を追加。`stamina` の組は残す |
| `dashboard` / `analytics` のグラフ | `fatigue` の系列を追加し、切り替え日に注記 |
| `app/Support/LogMetrics.php` | 3か所にある `$scores` 定義を一元化（前回計画の Refactor） |
| `tests/Pest.php` `logPayload()` | `stamina` → `fatigue` に差し替え（`fatigue` が必須になるため、ここだけは変えないと既存テストが全部落ちる） |

> 体の不調は Step 1 の「体の痛み・不調」で別に記録されるため、疲労度は「疲れ」だけを測る項目にできる。

### Step 5: 翌朝の余裕（旧フェーズ6 の一部）

| 対象 | 内容 |
|---|---|
| マイグレーション | `logs.morning_capacity` smallint nullable ＋ CHECK `0..10` |
| `form.blade.php` | 「数値」セクションに任意スライダー（起きたときの余裕・高いと余裕あり）。Step 2 のコントロール可能度と並べる |
| `AnalyticsService` | `CORRELATION_PAIRS` に `morning_capacity × mental_capacity`（同じ日の朝→夕方）、`AUTOCORRELATION_PAIRS` に `mental_capacity → morning_capacity`（前日の夕方→翌朝） |
| テスト | 前回 T6-1・T6-3・T6-4・T6-5 のうち `morning_capacity` の分 |

> 「その日の朝」の値なので、夜に入力するときに思い出して入れる形になる。翌朝に入力する運用は求めない。

## 4. 要判断（着手前にご確認いただきたい点）

| # | 内容 | 選択肢 | 推奨 |
|---|---|---|---|
| **D** | 「その他」で繰り返されている回復行動を、どのラベルで追加するか | D-1：具体的なラベルを**管理画面から**追加（seeder＝public リポジトリには書かない）／D-2：一般的なラベル（例：「人と話す・飲みの場」）で seeder に追加／D-3：追加しない | **D-1**。本人が分かるラベルにしたいが、共通マスタの seeder は public リポジトリに残るため |

| **F** | 強度を ○ のとき必須にするか | F-1：必須（過去ログの編集時は任意）／F-2：任意 | **F-1**。効いた感で実績がある方式 |
